# ADF Watermark Ingestion Pipeline

This folder contains the Azure Data Factory (ADF) pipeline that incrementally
loads data from the PostgreSQL OLTP source (`database/`) into the ADLS Gen2
raw zone, using a per-table watermark stored in a separate Azure SQL control
database.

```text
PostgreSQL (retail_oltp) --> ADF (watermark filter) --> ADLS Gen2 raw zone
                                    ^
                                    |
                     Azure SQL (watermark-db): pipeline_config,
                     pipeline_watermark_control
```

`adf_pipelines/` is not hand-edited — every file there is generated by ADF
Studio's Git integration when you build or edit objects in the Studio UI, and
gets auto-committed to `main` (the collaboration branch). Publishing from
ADF Studio compiles this into ARM templates on the `adf_publish` branch,
which is what actually gets deployed to the live Data Factory.

## Linked services

| Name | Type | Connects to |
|---|---|---|
| `ls_postgres_dev` | Azure Database for PostgreSQL | `retail-pipeline-dev-pg.postgres.database.azure.com` / `retail_source`, SQL auth (`pgadmin`), password from Key Vault |
| `ls_sql_watermark_ctrl` | Azure SQL Database | `retail-pipeline-dev-sql.database.windows.net` / `watermark-db`, SQL auth (`sqladmin`), password from Key Vault |
| `ls_adls_dev` | ADLS Gen2 | `retailpipelinedev.dfs.core.windows.net` |
| `ls_key_vault` | Azure Key Vault | `retail-pipeline-dev-kv` — supplies the two SQL passwords above as secrets (`postgres-admin-password`, `sql-admin-password`) |

## Datasets

All three are parameterized so a single dataset definition is reused across
every table, rather than one dataset per table:

| Name | Points at | Parameters |
|---|---|---|
| `ds_postgres_data` | `retail_oltp.<table_name>` via `ls_postgres_dev` | `table_name` |
| `ds_watermark_ctrl` | `dbo.<table_name>` via `ls_sql_watermark_ctrl` | `table_name` (used for both `pipeline_config` and `pipeline_watermark_control`) |
| `ds_raw_adls` | `raw/<table_name>/year=YYYY/month=MM/day=DD/<table_name>_<run_id>.json` via `ls_adls_dev` | `table_name`, `year`, `month`, `day`, `run_id` |

## Pipeline: `pl_load_data`

1. **`lkp_active_pipeline_configs`** (Lookup) — reads `pipeline_config` where
   `is_active = 1`, returning every table currently enabled for ingestion
   (name, watermark column, lookback window).
2. **`foreach_active_table`** (ForEach, sequential) — loops once per row
   returned above. Everything below runs per table, per iteration:
   - **`lkp_current_watermark`** (Lookup) — reads that table's
     `last_watermark` from `pipeline_watermark_control`.
   - **`copy_to_raw_zone`** (Copy activity) — pulls rows from
     `retail_oltp.<table>` where
     `updated_at > (watermark - lookback_days)` and `<= now()`, and lands
     them as JSON in the ADLS raw zone, partitioned by UTC date.
   - **`sp_update_watermark`** (Stored Procedure) — calls
     `usp_update_watermark` to advance `pipeline_watermark_control` to the
     current run's timestamp, recording rows loaded.

Because everything is driven by `pipeline_config`/`pipeline_watermark_control`
data rather than hardcoded per table, adding a new table to ingestion is a
pure data change — flip `is_active = 1` for it in `pipeline_config` — no
pipeline edits or republish required.

## Running it

- **Manual**: open `pl_load_data` in ADF Studio, click **Debug** (test run,
  doesn't affect the published trigger schedule) or **Trigger now** (uses
  the published version).
- **No scheduled trigger is configured yet** — this pipeline currently only
  runs on demand.

## Verifying a run

```sql
-- Azure SQL (watermark-db): confirm watermarks advanced
SELECT * FROM dbo.pipeline_watermark_control ORDER BY updated_at DESC;
```

Check the ADLS `raw/<table>/year=/month=/day=/` folder (UTC date, not local)
for that run's landed file, named `<table>_<pipeline_run_id>.json`.

## Known limitations

- No scheduled trigger — manual/on-demand only.
- The window end is frozen once per run. `set_window_end` writes the
  `window_end` variable before the loop, and the Copy activity's upper bound,
  the raw-zone path and the Stored Procedure all read that one value. This
  closes the earlier gap, where `utcnow()` was evaluated independently in each
  place and rows whose `updated_at` landed between the Copy's upper bound and
  the recorded watermark were skipped. With `lookback_days = 0`, as on
  `exchange_rates`, those rows were never picked up again.
  **Not yet validated.** These edits were made directly in the repository JSON
  while the factory was torn down, so they have never been through Studio's
  Validate all, and have never been published or run. At the next bring-up,
  before Publish: open `pl_load_data` in Studio, run Validate all, then Debug,
  and confirm `last_watermark` matches the `<=` bound in the Copy activity's
  resolved query, identically for all 12 tables.
- No row-count reconciliation. `rows_loaded` stores `rowsCopied` but is never
  compared with anything, so a partial copy that still reports Succeeded
  advances the watermark. The intended check is `rowsRead` against
  `rowsCopied` inside `usp_update_watermark`, held until a Debug run confirms
  the Azure PostgreSQL connector actually populates `rowsRead`.
